# Decisions

Format: context → decision → alternatives rejected → cost / revisit trigger.
Status: ACCEPTED, TENTATIVE (pending stated evidence), PENDING-USER.

## D1 InferEvo is a research layer over in-place sibling repos (ACCEPTED)
Context: Simthesizer fork (`test_dev`) already integrates RoofLang (shared
operator-level execution, Kimi-K3, P/D, policy search); both repos carry
uncommitted user work.
Decision: InferEvo holds orchestration, contracts, registry, evaluator,
ledger and docs; it imports/executes `../simthesizer` and `../rooflang`
in place and pins `commit + dirty-diff sha256` per result
(`adapters/engines.py`). Engine/cost-model changes happen *in those repos*
on isolated worktree branches (D8), never as copies inside InferEvo.
Rejected: (a) vendoring both into a monorepo — third copy, drift; (b) new
simulator — duplicates working, tested capability (spec 4.4.1).
Cost: cross-repo identity management. Revisit: if upstreaming is desired.

## D2 Simthesizer is the system simulator; RoofLang prices operators (ACCEPTED)
Engine owns time; Simthesizer resource domain owns rates/capacity; KvRuntime
owns state; scheduler owns token progress; RoofLang owns graph structure,
per-operator FLOPs/bytes/dtypes, transfer bytes/routes, hardware graph.
Matches the existing shared path and spec 4.3. RoofLang's own DES remains
the isolated reference and the standalone static-batch DSE tool.

## D3 Two execution granularities (ACCEPTED 2026-11-25, E0008/E0009)
- Tier-2 *Execution DAG*: existing shared path (operator-level native nodes,
  contention, state). Used for new mechanisms, contention, final evaluation.
- Tier-1 *Cost Query*: iteration-level latency/footprint from RoofLang for a
  `(model, hw, layout, stage, batch aggregates, cost_model_version)` key,
  memoized + interpolated, consumed by a cheap runner for large search.
Evidence: Kimi Tier-2 costs 164–528 s for 10 requests.
Pending: Phase 1 measurement of Tier-1 error vs Tier-2 on identical batches
(acceptance: per-iteration error budget recorded; screening only, never final
evaluation). Cache key includes the cost-model hash so model changes
invalidate entries.
Rejected: running full RoofLang search per decode step (spec 6.2).

## D4 Single charge rule (ACCEPTED)
Every simulated cost must come from exactly one owner: a RoofLang demand
executed by the resource domain, or a declared native transfer/logical
latency. A RoofLang collective already priced is never re-timed natively.
Validator checks demand coverage and byte conservation per round.

## D5 Hardware facts have one sourced home (ACCEPTED)
`validation/hardware.py` records per-field value, unit, status, source.
RoofLang presets stay the executable model; `audit_preset()` turns any
deviation into a cost-model change request (D6), never a silent edit.

## D6 Cost-model changes use a separate change process (ACCEPTED)
Covers presets, kernel formulas, efficiency/calibration parameters. Each
change: change record, version id (hash), re-evaluation of baseline and all
compared candidates under the new version. Ordinary mechanism candidates
cannot modify cost-model files (spec 10.2). First queued changes:
CM-1 H200 MXFP4 → explicit dequant+BF16/FP8 path (no native FP4);
CM-2 H200 capacity 141 GB; CM-3 B300 HBM 8 TB/s; CM-5 adopt upstream
RoofLang #10 (MLA prefill uses full-MHA width qk+v=320 instead of absorbed
576+512=1088 per pair/head; local copies overstate prefill MLA attention
FLOPs 3.4×); CM-4 efficiency/launch
parameters as explicit, sourced, sensitivity-swept knobs (default = current
peak behaviour, labelled "roofline upper bound").

## D7 Component registry = manifest over existing kind registries (TENTATIVE)
Reuse Simthesizer link-time `kind` registries and RoofLang module layout.
InferEvo keeps a manifest per component (owner repo/path, interface, state
owned, depends_on, tests, invariants), partly generated by scanning
`register!` macros and bridge modules. Impact = reverse-dependency closure;
regression selection = tests attached to the closure.
Rejected: a new plugin framework wrapping both repos (over-abstraction).

## D8 Candidate isolation via git worktrees of both repos (ACCEPTED)
Baseline snapshot = pinned commit + captured dirty patch (stored under
`mechanisms/versions/`). Candidate = worktree branch `inferevo/<cand>` from that
snapshot in each repo it touches. User working trees are never modified.
Existing Docker launchers remain the option for agent runs needing process
isolation.

## D9 Frozen evaluator outside candidate trees (ACCEPTED)
Evaluator code, workloads, SLOs, metric formulas and cost-model version live
in InferEvo `evaluation/` with hashes; it executes candidate binaries/workers
by path and writes receipts. Candidates cannot write evaluator files or
receipts (spec 10.1; RSIBench-Infra principle, to be audited).

## D10 One cross-layer feedback schema built from existing outputs (TENTATIVE)
Levels: operator, layer, GPU, link, worker/instance, request, agent session.
Sources: Simthesizer `--reports` CSVs (operator-costs, rounds, kv-*, memory),
result JSONL/metrics, RoofLang dense_feedback V0.1. Normalization only; no
new timing semantics. Bottleneck classes per spec 4.4.3 (critical path vs
total, hidden vs exposed, contention, imbalance, scheduling).

## D11 Evidence ladder for every claim (ACCEPTED)
`MATH_VERIFIED` (CPU reference) → `PHYSICALLY_FEASIBLE` (resource/topology
/precision checks) → `SIMULATED` (Tier-2, frozen evaluator) →
`ROBUST` (holds across sensitivity band) → `CALIBRATED` (public data) →
`HARDWARE_VERIFIED` (never available here). Reports must state the level.

## D12 Agent controller reuses existing launchers and state machine (TENTATIVE)
No new multi-agent framework. Controller = deterministic state machine
(qwen_moe_optimization DESIGN §3 states) + ledger in InferEvo; agent work
units are CLI sessions (Codex/Claude) via existing Docker launchers with
rendered task files and skills. Revisit after first closed loop (Phase 4).

## D13 Capacity layouts generalized from the executed bridge (ACCEPTED)
`validation/capacity.py` calls `rooflang_bridge.kimi_k3._weight_layout` /
`state_schema` (the code the simulator executes) for arbitrary N / attn TP,
instead of re-deriving byte formulas. Reproduces the documented
122,651,032,104 B/GPU at 16×H200 TP2 exactly.

## U1 Frozen precision contract for Kimi-K3 (ACCEPTED by user 2026-11-24: official precision)
Official checkpoint (verified from tensor names): MXFP4 routed experts, BF16
everything else, BF16 KV. Current RoofLang/bridge: FP8 attention, shared-
expert and dense-MLP projections and FP8 MLA cache (latent projections,
router already BF16).
Impact: +~57 GB total weights; at 16×H200 TP2 the official precision does
not fit (bridge path is already within 4.2 GB). Changes every H200 baseline.
Recommendation: freeze **official precision** as the baseline semantics;
treat FP8 non-expert/KV quantization as an explicit mechanism candidate with
a quality-constraint flag (spec 4.4.9: semantics-changing optimizations need
separate quality constraints). Until decided, results are labelled with the
precision profile used.

## D14 Reference repositories live in `../github/` (ACCEPTED, user 2026-11-24)
Pristine upstream clones (e.g. `github/rooflang` yzygitzh @4ff475d,
`github/Simthesizer` casys-kaist @ebd06db) are read-only references for
audits and upstream diffs. Further reference projects are cloned there on
demand, pinned by commit in TECH_SOURCE_MAP.md. Never executed as part of
the simulator unless adopted through a change record.

## D15 Kimi shared layouts generalized; default H200 TP4/EP16 (ACCEPTED)
Context: under MC-1, TP2/EP16 needs 147.2 GB/GPU > 144 GB H200 preset.
Decision: shared path accepts H200/B300, Attention TP 1/2/4/8, EP | 896 with
EP % TP = 0, GPU count = EP; legality has one home
(`kimi_k3_shared.validate_parallel` + Rust runner check; CLI only checks
allocation consistency). Default TP4/DP4/EP16 (118.8 GB/GPU). Pulled forward
from ROADMAP Phase 2 because no H200 baseline was otherwise feasible.

## D16 Active research trees (SUPERSEDED by D17)
`baselines/active.json` names the worktrees InferEvo analyses by default;
`INFEREVO_SIMTHESIZER/ROOFLANG` override. User trees remain untouched
(`workspace.USER_*`). Snapshot/branch records in `baselines/*.json`.

## D17 Repository layout by responsibility (ACCEPTED, user 2026-11-25)
engines/ (runtime worktrees), references/ (read-only, symlinks to ../github),
adapters/, mechanisms/, validation/, agent/, experiments/, docs/. Root keeps
the name InferEvo because engine worktree paths are recorded in the user
repos' git metadata. Dependency direction: validation → adapters;
mechanisms → adapters; experiments → all; nothing imports experiments.
Experiment results are keyed by cost-model version so reruns never overwrite
evidence.

## D18 Tier-1 = fitted StepTime over batch aggregates (ACCEPTED)
Evidence: per-step evaluation of the exported graph is exact enough (engine
within ~1 % of its bound, E0008) but costs 0.24–2.5 s/step — slower than
Tier-2. A linear model over physical aggregates (max requests/kv/q/attention
pairs per Attention group, expected expert fraction touched, tokens), fitted
to graph bounds of random batches, predicts engine decode rounds with median
1.07 % / p90 4.0 % error at 3 µs/query (E0009). Interface mirrors BLIS
`StepTime(batch)`. Keyed by (hw, TP, EP, stage, efficiency profile,
cost_model_version); re-fit on any change. Screening only.
Next: drive Simthesizer's own scheduler/P-D with Tier-1 via a native runner
(no re-implemented serving loop, spec 4.4.1).

## D19 Tier-1 runs inside Simthesizer as a native runner (ACCEPTED)
`step_model` (Rust kind) prices one logical node per iteration from fitted
coefficients and request-aware Attention-group features; Simthesizer's own
scheduler, P/D system and multi-rail KV topology run unchanged. Required
engine changes: `supports_attention_dp()` capability (non-shared runners that
honour `request_id % groups`), SIM-DEFECT-2 (fixed state in non-shared
handoff), scalar Kimi model (`kimi_k3_scalar`), and per-rank scheduler limits
(legacy scheduler multiplies max_batch/max_num_batched_tokens by EP; the
adapter divides). Wall: ~1 s vs 194 s Tier-2 on the frozen workload.
Targets: decode = graph lower bound (tight, E0008); prefill = Tier-2 engine
rounds (graph bound 1.7x optimistic at 128 tokens, E0012).

## D20 Agent programs via a composable front end (ACCEPTED)
`agent_dag` (Simthesizer system kind) owns agent-program DAGs and seeds each
LLM call into any single-LLM system (P/D, Tier-1 or Tier-2) through sinks,
instead of extending P/D's lifecycle (Simthesizer rule: compose via seeding
and sinks). Closed loop: dependents release on completion + tool duration +
think interval. Verified identical to native single_instance DAG execution.
Calls carry full context (workload contract); KV retention across calls is a
mechanism candidate (C-KVRETAIN), not baseline behaviour.

## D21 Controller search: best-first with dimension coverage (ACCEPTED)
Candidates = policy (diagnosis) moves + one coverage probe per dimension
(`neighbours`), proposed from every evaluated deployment; the next
evaluation is the candidate whose parent has the highest SLO goodput,
diagnosis moves before probes. Evidence: BFS over rules alone reached HV
0.54 (below random 0.87) on the 18-point TP × budget × P:D space because no
rule mentions TP (E0021); best-first + coverage: HV 0.998, goodput-best in 5
of 18 evals; on E0019's 9-point space HV 1.00 at both loads. Rules encode
domain knowledge; coverage keeps unknown dimensions reachable; the LLM
policy plugs into the same `policy(entry)` interface.
SLO for goodput is an explicit assumption (TTFT ≤ 2 s, TPOT ≤ 50 ms),
recorded per ledger entry.

## D22 Capacity probes: duration-scaled runs, decode-backlog check (ACCEPTED)
A capacity probe at rate r simulates max(600, r x 300 s) requests, and a
probe is stable only if neither queue grows: prefill (TTFT, as before) and
decode (decode time = e2e − TTFT, last-third p50 ≤ 1.25x first third).
Evidence: once PP2xEP8 made prefill 4.6x faster (E0033), fixed 600-request
probes accepted 12.2 req/s on 128 GPUs although delivered throughput was
29 of 98 tok/s/GPU (calls queued for decode slots: one long inter-token gap,
invisible in mean TPOT), and still 7.83 req/s with the decode check alone
(2000 requests at that rate: TTFT p50 5.6 s, attainment 0.40). With both
fixes the optimum is 7.34 req/s with delivered 57.4 of 58.7 tok/s/GPU.
Earlier capacities (E0028, E0030) used fixed request counts; E0030 (2.4
req/s, 250 s of arrivals) is near this rule, high-rate E0028 short-workload
values (22 req/s, ~90 s) may be optimistic and should be rerun before reuse.

## D23 Tier-1 layout coverage requires a held-out load check (ACCEPTED)
A layout's surrogates (adapters/fit_layout.py) are fitted on Tier-2 prefill
samples + decode graph bounds, load-calibrated by one scale per side on run
A, and checked on a different loaded run B. A side is usable only if its
held-out error is <= 5 % (TTFT for prefill, TPOT p50 for decode,
`agent.controller.DECODE_HELDOUT_MAX`); otherwise the layout is prefill-only.
Evidence: prefill calibrations transfer (B within 1 % for PP2xEP8, PP4xEP4,
TP8 PP2xEP8); decode scales do not always (B TPOT +6.6 % PP4xEP4, +15.5 %
TP8 PP2xEP8, −0.4 % PP2xEP8 TP4). Decode batches > 32 additionally need a
Tier-2 run whose reconstructed rounds reach that batch (E0037: runs A/B never
exceeded 12 requests per round; run C validates ~64).


## D24 Feedback granularity for the search agent: resource (ACCEPTED)
The agent diagnoses the bottleneck side from per-side queue growth, else
the SLO split, and the resource bounding that side's round (graph-bound
elasticity to compute/memory/network x0.5, `agent.search.attribution`); a
network-bound side tries layouts with EP inside one NVLink node first.
Evidence: E0042 (5 regimes, side counterfactuals x2): diagnosis matches
the counterfactual 5/5 with queue or resource feedback, 3/5 with the SLO
split only (fails on decode backlog), 0/5 without; evaluations to the best
move 1.0 / 2.2 / 3.4 / 4.0. Held-out whole searches (E0043, 16 evals):
resource = queue >= slo >> none (best capacity 100 / 100 / 63–100 / 9–77 %);
on 64 GPUs both find the 99-point grid optimum. The resource rule was
designed on E0042 R1/R3; its held-out gain is small (one problem, 10 vs
14 evals).

## D25 Mechanism lifecycle and A–E evaluation (ACCEPTED)
Phase 4 realises D7–D9: `mechanisms/registry.py` scans the component graph
(Rust paths/registrations, Python imports, launchers, binary use, curated
`components.toml`); `mechanisms/spec.py` validates a spec (spec 8.2) and
plans extension order, impact closure and regression tests;
`mechanisms/manage.py` runs DRAFT -> CHECKING -> EVALUATING -> REPLAYING ->
VERIFIED | EXPLORATORY | FAILED -> PROMOTED with receipts (evaluator
hashes) and `mechanisms/lineage.jsonl`. `check` = declared-vs-actual
diff, release+debug build, selected regression tests, default-off identity
(`mechanisms/identity.py`: Tier-2 PP1xEP16, PP2xEP8, Tier-1 optimum,
byte-identical results), spec checks. Every mechanism's design variables
default to the off state. A–E per mechanism: A parent semantics, B best
existing configuration, C mechanism on, D mechanism co-searched with
existing variables, E controls (conservation, negative case, launch-cost
robustness). Promotion is a fast-forward of the engine branch only.
Amendment (M-RANKDISPATCH r0): a control must show the mechanism is
exercised. r0's decode control decoded one call per attention group (16 x
2048 prompts left prefill 0.6 s apart), so dispatch shares never split and
the run was byte-identical to the parent; the verdict was withdrawn and the
candidate revised (r1). Evaluation scripts now record the exercised regime
(E0047 guards peak decode concurrency >= 2 per group); receipts of earlier
attempts are archived, not overwritten.

## D26 Semantics-changing mechanisms are opt-in and quality-flagged (ACCEPTED, user 2026-11-27)
The user asked for decode-side precision mechanisms. The official checkpoint
precision (U1: MXFP4 routed experts, BF16 elsewhere, BF16 MLA KV, FP32 KDA
state) stays the baseline. A precision mechanism declares `[quality]` in its
spec (status, sourced evidence and its limits); its verdict covers
performance only; promotion records the quality status in the lineage;
searches use it only with `--allow-fp8` (`Problem.allow_precision`) and
results print the flag. Quality is never simulated here. First instance:
M-FP8LINEAR (DeepSeek-V3 FP8 recipe; the cited <0.25 % loss gap is FP8
training, not post-training quantization of a BF16-trained model).

## D27 Tier-1 surrogates have non-negative coefficients (ACCEPTED)
Every Tier-1 fit (graph-bound decode anchors, prefill round sums, load
calibration inputs) is a non-negative least-squares fit of relative error
(`adapters.tier1.nnls`): round time is monotone in every feature. Evidence:
unconstrained fits cancelled collinear KV features and extrapolated decode
recompute rows (preemption) to negative time, producing the zero-gap tokens
of SIM-DEFECT-3; in-domain accuracy is unchanged by the constraint
(prototype held-out TPOT −0.8 % both). As a cost-model-level change (D6) it
re-evaluates the Tier-1 baselines: all surrogates refitted, E0052 Tier-1
side, E0055 and E0057 re-scored.

## D28 Evaluation scale: 128 GPUs (ACCEPTED, user 2026-11-28)
All tests and evaluations use 128-GPU deployments: Tier-1 searches and
capacity checks, Tier-2 confirmations and mechanism A–E evaluations. The
per-instance (P1:D1, 32 GPUs) Tier-2 confirmations E0052 / E0060 and the
P1:D1 mechanism bursts E0044 / E0047 / E0049 / E0051 stand as recorded;
new confirmations run the full 128-GPU deployment (~5-6 h Tier-2, in the
background). Surrogate fitting stays per layout (calibration, not a test).
